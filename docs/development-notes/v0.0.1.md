# v0.0.1 Development Notes

この文書は、Ariadne AI Workflow Platform の v0.0.1 時点の開発内容を、後続の GitHub Issue、Pull Request、RAG、改善計画へ再利用できるように残すための開発ノートです。

`v0.0.1` は、この文書上の開発節目として扱います。現時点では Git tag は存在せず、記録対象の基準は `main@be4f991` です。`runtime/pyproject.toml` の package version `0.1.0` とは別の、repository 全体の初期整理単位です。

## Goal

このバージョンで達成したかったことは、AI Agent が対象システム開発、改善、文書同期、知識化を進めるための「ローカルファーストな workflow platform」を成立させることでした。

特に重視した目標は次の通りです。

- 人間の判断、AI Agent の作業、runtime helper の実行責務を分ける。
- workflow 実行前に repository、branch、環境、tool、成果物の前提を Context として残す。
- GitHub Issue、Pull Request、commit、docs、RAG source を、後から読み返せる知識資産として扱う。
- 要件定義、改善、docs-sync、knowledge capture、RAG build/load、IaC、GUI、VSCode environment などの workflow entrypoint を整理する。
- Windows 11 PowerShell、POSIX Bash、`aiwfctl` の入口を用意し、作業者や Agent が同じ操作体系で runtime を呼べるようにする。
- 日本語成果物を既定とし、UTF-8、BOM、mojibake、console encoding の問題を workflow 品質として扱う。
- 生成物を `work/` に閉じ込め、Git 管理する source of truth と作業中 artifact を分離する。
- pytest と runtime health check により、workflow helper の変更を検証できる状態にする。

この段階の成功条件は、単一の完成アプリを作ることではなく、今後の開発案件を「要件、設計、実装、検証、証跡、知識化」まで同じ型で回せる土台を持つことでした。

## Architecture

v0.0.1 時点の構成は、prompt、Skill、runtime、schema、docs、template、work artifact、RAG artifact を分離する repository-local architecture です。

```text
.github/
  agents/      role-based Agent prompt
  prompts/     slash command style workflow prompt
  schemas/     Agent間共有JSONとruntime artifactのschema
  shared/      共通policyと運用ルール

docs/
  workflows/   workflow別の運用ガイド
  reference/   runtime、data model、RAG、operationsなどの参照文書
  governance/  platform全体の設計原則と運用統治
  diagrams/    workflow mapとflowchart
  brand/       Ariadneの思想、名前、logo asset

runtime/
  common/      aiwfctl、registry、Context、Human Gate、共通utility
  workflow/    workflow別runtime helper
  github/      GitHub Issue / PR helper
  scm/         repository準備、branch、commit、push helper
  rag/         normalize、chunk、index、embedding、retrieval
  environment/ tool/package preflight
  tools/       Windows向けcmd wrapper、encoding tool、PATH登録
  windows-ps1/ Windows PowerShell native entrypoint
  posix-bash/  Linux / WSL / macOS Bash native entrypoint

skills/
  */SKILL.md   Codex workflow entrypoint
  skill-index.json

templates/
  artifacts/   requirements、design、process report、test evidence
  boilerplates/ apps、services、infrastructure、integration、mcp
  workflows/   workflow固有template

db/
  registries/  aiwfctl / dispatcher / human gate用 DuckDB registry
  rag/         生成済みRAG read model

work/
  requirements/ draftと完成版要件定義書
  <work-id>/   workflow実行中artifact
  db/          knowledge source repository cloneとRAG source
```

設計の中心は Context First Architecture です。

```text
Human input / requirement / command
  -> Dispatcher Context
  -> Workflow Runtime
  -> Agent Prompt / Skill
  -> Work Artifact
  -> Test Evidence / Process Report
  -> Docs / GitHub / RAG candidate
```

`work/<work-id>/context/context-manifest.json` を索引とし、`environment-selection.json`、`workflow-selection.json`、`tool-selection.json`、`runtime-context.json`、`execution-plan.json` などを段階的に増やす方針です。Workflow は Dispatcher Context を独自推論で上書きせず、実行結果として `workflow-state.json` や workflow 固有 context を作ります。

Runtime の正式入口は `aiwfctl` / `runtime/common/ctl.py` です。Windows 11 では `runtime/windows-ps1/aiwf.ps1`、POSIX では `runtime/posix-bash/aiwf.sh` を薄い shell wrapper とし、workflow 判断は `aiwfctl` 側へ寄せています。

GitHub 周辺は、GitHub API / `gh` と Git CLI local / remote の責務を分離しています。Issue、PR、comment、label、release などは GitHub metadata として扱い、commit graph rewrite や tree diff 検証は Git CLI local の責務にしています。remote push や force-with-lease は Human Check 後の Git CLI remote 操作として扱います。

RAG は file-based pipeline です。

```text
source Markdown
  -> normalized UUID JSON
  -> chunk JSON
  -> JSONL indexes
  -> local embeddings
  -> retrieval result / context pack
```

この方針により、将来 DB や外部 vector store へ移行する前でも、人間が読める Markdown と Git diff で知識の形を確認できます。

## Major Changes

### Workflow Platform の初期整備

- `/requirement-discovery`、`/ariadne-new-system`、`/ariadne-feature-maintenance`、`/corrective-action-report`、`/corrective-action-fix`、`/docs-sync`、`/knowledge-capture`、`/rag-build`、`/rag-load`、`/github-knowledge-maintenance` などの主要 workflow を Skill と docs へ整理しました。
- workflow prompt と Agent prompt を `.ariadne/prompts/`、`.ariadne/agents/` に分け、Skill は `skills/<name>/SKILL.md` を entrypoint にしました。
- workflow ごとの成果物を `work/<work-id>/` に保存し、要件、設計、process report、test evidence、context を同じ棚で扱う前提を作りました。

### Context First / Dispatcher First の導入

- `context-manifest.json` を中心に、workflow が最初に読むべき context を明示する設計を導入しました。
- Environment Dispatcher により、`aiwfctl env select <environment>` で `environment-selection.json` を作れるようにしました。
- workflow、tool、runtime、execution plan を Dispatcher Context として段階導入する設計を docs と schema に残しました。
- Context 不足時は推測で進めず、Context 生成または Human Check に戻す方針を明文化しました。

### aiwfctl / Runtime Entry Point の整備

- `runtime/common/ctl.py` を runtime helper の正式入口として整理しました。
- `runtime/tools/aiwfctl.cmd`、`runtime/tools/register-aiwfctl-path.cmd`、`runtime/windows-ps1/aiwf.ps1`、`runtime/posix-bash/aiwf.sh` を整備し、Windows / POSIX の入口を分けました。
- `aiwfctl help list/show/search/open/markdown` により、workflow command と extension を terminal から検索できるようにしました。
- `aiwfctl env` により、利用者向け environment 名と内部 backend profile の境界を明確にしました。
- runtime helper は `uv run --project runtime python ...` を標準にし、Python 実行環境を repository-local に寄せました。

### Registry の DuckDB 化

- workflow help、search terms、tool candidates、human gates、workflow environments、environment profiles、environment mappings を `db/registries/registry.duckdb` へ集約しました。
- 旧 JSON registry は source backup として `work/db/ariadne-knowledge-platform/registries/` 側へ分離しました。
- schema は `.ariadne/schemas/`、runtime が読む registry 実体は `db/registries/` として責務を分けました。

### GitHub Knowledge Maintenance の強化

- GitHub repository を長期的な知識資産として保守する `/github-knowledge-maintenance` workflow を整備しました。
- Issue、PR、comment、docs、CAR、commit source、commit message、semantic commit subject、RAG candidate を解析対象にしました。
- GitHub API / `gh` と Git CLI local / remote の責務分離を明文化しました。
- 1-3 file の commit 漏れや不自然な履歴を small rebase candidate として検出、計画、Human Review、非対話 replay、検証、必要時 push へ進める runtime を整備しました。
- `rebase-package`、`rebase-apply`、`publish-verified-replay`、`message-repair-plan`、`message-review-intake`、`message-repair-package` などの経路を追加し、commit rewrite を ad hoc script ではなく schema 準拠 package と runtime 実行に寄せました。
- GitHub sync は未解決の rebase candidate がある場合に停止するようにし、歴史整備と GitHub metadata 補修の順序を守る設計にしました。

### Encoding / UTF-8 / BOM 対応

- 日本語 docs、prompt、report を前提とするため、UTF-8 を共通認識とする設計を追加しました。
- `runtime/tools/text_encoding_convert.py`、`runtime/tools/text_encoding_guard.py`、`runtime/tools/utf8_bom.py` を整備しました。
- PowerShell console の表示化けだけで Markdown / JSON の破損を判断しない方針を明文化しました。
- BOM scan / strip、strict decode、不可逆欠落検出を workflow 品質の一部として扱うようにしました。

### RAG Pipeline と Knowledge Source の整理

- Corrective Action Report、GitHub Knowledge、Workspace Environment、External Web、Specialist Review などの RAG source を整理しました。
- source Markdown から normalized UUID JSON、chunk、index、embedding、retrieval result へ進む file-based pipeline を定義しました。
- 外部Web由来の知識は本文保存ではなく、claim、metadata、verification notes、URL を保存する補助知識として位置づけました。
- RAG は current repository evidence を上書きしない補助情報として扱う方針を明文化しました。

### Workflow Extension / Boilerplate の追加

- GUI SVG から PyQt6 / QTest 候補を作る `gac-uac-gui-mode` を workflow extension として整理しました。
- Web SVG から React / Playwright 候補を作る `web-svg-layout-mode` を追加しました。
- Next.js webapp 実装前準備、Flutter multi-platform、MCP server group、realtime IaC、system integration quality、VSCode environment などの workflow extension と docs を整備しました。
- app、service、infrastructure、database、middleware、integration、MCP の boilerplate を追加・整理しました。
- OpenTelemetry boilerplate、Redis、DB、microservice infrastructure など、対象 system の構成要素を増やしました。

### Test / Evidence / Runtime Health

- `runtime/tests/` に runtime helper の pytest を整備しました。v0.0.1 時点で runtime test file は 40 件あります。
- `docs/reference/runtime-pytest-ut/` に UT 仕様を置き、pytest node id 単位の仕様と実装を対応づける方針を取りました。
- test evidence の保存先を `work/<id>/test-evidence/` と target repository の `docs/evidence/issue-<issue-number>/` に分けました。
- `workflow_doctor`、coverage audit、UT spec sync など、Ariadne 自身を検査する runtime を追加しました。
- push 前にはテスト仕様、実行ログ、人間確認結果などの実 evidence を確認し、scaffold README だけでは証跡扱いにしない方針にしました。

### Workspace / Git 管理ルール

- `work/**` の作業実体、生成 registry、agent workspace、pytest 生成物などを Git 管理から外すルールを整備しました。
- `work/**/README.md` は追跡対象にできる一方、source checkout、`.git/`、`.venv/`、`node_modules/`、build artifact は追跡しない方針にしました。
- `work/close/` は重い source checkout ではなく、report-only archive として扱う方針を定義しました。
- `runtime/constants/` に workspace path や schema path の定数を集約し、ハードコーディングを減らしました。

### Brand / Governance Docs

- Ariadne という名前、糸巻きの motif、Context First の思想、Human Responsibility を brand docs と governance docs に整理しました。
- `docs/governance/ariadne/architecture-principles.md` で、責務分離、Context First、Dispatcher First、Human Check、Runtime Observability、UTF-8、再利用性、ローカルファースト、Knowledge 構造化を原則化しました。
- repository の目的を、単なる tool 集ではなく AI workflow platform として説明できる状態にしました。

## Design Decisions

### 1. Conversation ではなく Artifact を source of truth にする

AI Agent との会話だけに判断を閉じると、後続の workflow が同じ前提を再利用できません。そのため、要件、設計、判断、証跡、Human Check、RAG 候補を file artifact として残す設計にしました。

この判断により、Agent が変わっても `work/<work-id>/context/`、`process-report/`、`test-evidence/`、`docs/` を読めば作業の再開点を復元できます。

### 2. Context First で AI の推測負荷を下げる

AI Agent は前提が欠けていると補完しようとします。これは便利ですが、repository、branch、tool、環境、承認状態を誤ると重大な事故になります。

そのため、Dispatcher Context を先に生成し、workflow はそれを第一入力として読む設計にしました。推測を禁止するのではなく、推測が必要な場所を Context 生成と Human Check へ戻す形にしています。

### 3. Human Check は作業停止ではなく責任境界にする

push、GitHub mutation、install、RAG publish、commit rewrite、実機 I/O は、人間の責任領域を含みます。v0.0.1 では、Human Check を「AI が何もできない場所」ではなく「判断材料を揃えて人間へ渡す gate」として扱いました。

これにより、AI は調査、計画、証跡生成、command proposal まで進められますが、外部状態や履歴を変える操作は承認済み context を通して実行します。

### 4. GitHub API と Git CLI の責務を混ぜない

GitHub metadata の補修と Git commit graph の整備は性質が違います。GitHub token があっても local rebase はできませんし、Git CLI だけでは Issue / PR の説明不足は直せません。

そのため、Issue / PR / comment は GitHub API / `gh`、commit graph rewrite は Git CLI local、remote reflection は Git CLI remote として分けました。これは troubleshooting と Human Review の粒度を明確にするためです。

### 5. Commit rewrite は high-risk path として package 化する

履歴 rewrite は便利ですが、実行手順が会話や一時 script に埋まると再現性が落ちます。v0.0.1 では、small rebase や message repair を JSON package と runtime replay に寄せました。

この判断により、対象 candidate、repair goal、approval status、before/after SHA mapping、verification result を `github-knowledge-analysis.json` と process report に残せます。

### 6. Registry は runtime 横断の read model として DuckDB に寄せる

workflow help、search terms、tool candidates、human gates、environment profiles は、複数 runtime が読む共有情報です。個別 JSON を散らすと同期漏れが起きやすいため、runtime が読む実体は `db/registries/registry.duckdb` へ集約しました。

一方で、schema は `.ariadne/schemas/` に残し、source backup は `work/db/ariadne-knowledge-platform/registries/` に置くことで、構造、read model、知識 source の責務を分けています。

### 7. RAG は補助記憶であり、現在の repository evidence を優先する

RAG は過去知識の再利用に有効ですが、現在の source、test evidence、docs drift、Human Check を上書きしてはいけません。

そのため、RAG は source Markdown と normalized JSON による traceable な補助知識として設計しました。検索結果は supporting context であり、finding の確定には current repository evidence を必要とします。

### 8. Windows / POSIX の shell は薄く保つ

OS ごとに shell wrapper は必要ですが、workflow 判断を shell script に入れると分岐が増えます。v0.0.1 では PowerShell / Bash wrapper は encoding、repo root 解決、`uv run` 呼び出しなどの入口に限定し、判断は `aiwfctl` / Python runtime へ寄せました。

### 9. 日本語運用では encoding を品質要件にする

日本語 docs と report が多い repository では、mojibake は単なる表示問題ではなく、Agent の判断ミスや diff 汚染につながります。

そのため、UTF-8、BOM、PowerShell console 表示、strict decode、不可逆欠落を workflow concern として扱い、encoding tool と policy を追加しました。

### 10. Development note を versioned Issue の前段に置く

Issue は実行単位として優れていますが、version 全体の意図、設計判断、学びを Issue だけで追うと散らばりやすくなります。

そのため、`docs/development-notes/v0.0.1.md` のような version note を先に作り、そこから Issue を切る方針が有効です。Issue には作業単位、note にはその時点の全体像と判断理由を残します。

## Lessons Learned

- AI workflow は、prompt だけでは platform になりません。Skill、runtime、schema、docs、test、evidence、Human Check が揃って初めて再利用できます。
- 「あとで説明する」は負債になります。Issue、PR、commit、docs、RAG へ説明を残す導線を workflow に組み込む必要があります。
- Context がない状態で Agent に頑張らせるより、Context を作る runtime を先に整える方が安定します。
- GitHub 上の知識保守と Git 履歴の整備は、同じ「過去を直す」作業に見えても責務と危険度が違います。境界を分けたことで review しやすくなりました。
- Human Check は多すぎると儀式になりますが、対象操作、理由、command、rollback、verification を添えると実質的な安全装置になります。
- UTF-8 と console encoding は早めに扱うべきです。後から修正すると、docs、prompt、test fixture、report へ影響が広がります。
- 生成物の除外ルールは platform 初期に決めるべきです。`work/`、RAG read model、DuckDB、pytest cache、agent workspace が混ざると Git 履歴が読みにくくなります。
- registry を DB 化すると runtime からは扱いやすくなりますが、source backup、schema、更新手順、test をセットで持たないとブラックボックス化します。
- boilerplate は増やすだけでは足りません。どの workflow がどの boilerplate を選び、どの evidence で完了とするかまで docs 化する必要があります。
- test file 数を増やすだけでなく、UT 仕様、runtime health check、coverage audit、workflow doctor を組み合わせることで「platform 自身の品質」を見られるようになります。
- version note は単なる changelog より価値があります。Goal、Architecture、Design Decisions、Lessons Learned を残すと、次の Issue が「作業」だけでなく「なぜ今それをするか」から始められます。

## Next Version

次の version では、v0.0.1 で作った土台を、より運用しやすく、検証しやすく、Issue 化しやすい形へ育てます。

優先したいことは次の通りです。

- `docs/development-notes/` を versioned development note の正式置き場として docs index から参照できるようにする。
- 各 version note から GitHub Issue を切るための template を用意する。
- commit subject の semantic 化を進め、`update: ...` のような広い subject を減らす。
- GitHub Knowledge Maintenance の実行例を、read-only proposal、sync proposal、approved apply、RAG candidate で分けて docs に残す。
- Context First の Phase 3 を進め、workflow-selection、tool-selection、runtime-context、execution-plan をより多くの workflow で実運用する。
- `aiwfctl help` の検索語と説明を拡充し、日本語の自然文検索で目的の workflow に辿り着きやすくする。
- registry DuckDB の rebuild、summary、integrity check を CI または workflow doctor へより強く接続する。
- output language validation と encoding guard を通常の docs 更新フローに組み込む。
- RAG pipeline の normalize、chunk、index、embedding、retrieval を、workflow ごとの evidence と結びつけて検証しやすくする。
- close archive を使い、完了済み work folder の重い source checkout を report-only archive へ移す運用を固める。
- runtime tests と `docs/reference/runtime-pytest-ut/` の同期を継続し、テスト仕様の欠落を検出する仕組みを強化する。
- v0.0.2 以降では、機能追加だけでなく「運用で迷った点」「Human Check が多すぎた点」「Agent が誤解した点」を development note に残す。

Issue 化する場合の切り出し候補は次です。

| Candidate Issue | Purpose |
| --- | --- |
| Development note index | `docs/development-notes/README.md` を追加し、version note の読み方と作成ルールを定義する |
| Version issue template | version ごとの Goal / Architecture / Major Changes / Design Decisions / Lessons Learned / Next Version を Issue body template 化する |
| Semantic commit cleanup proposal | 既存 commit subject の弱さを GitHub Knowledge Maintenance で解析し、補修方針を提案する |
| Context First phase expansion | `workflow-selection`、`tool-selection`、`runtime-context`、`execution-plan` の実運用範囲を広げる |
| Encoding quality gate | output language validation、BOM scan、mojibake guard を docs / runtime workflow に接続する |
| Registry maintenance hardening | DuckDB registry rebuild、summary、schema consistency、test を一つの検証導線にまとめる |
| Close archive operation | 完了済み `work/` の軽量 archive と prune 手順を試験運用する |

v0.0.1 の結論として、Ariadne は「AI が作業する repository」から「AI workflow を運用、検証、改善、知識化する platform」へ移行する初期土台を持ちました。次は、この土台を日々の Issue 運用で摩耗しない形にしていく段階です。
