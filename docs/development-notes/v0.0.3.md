# v0.0.3 Development Notes

v0.0.3 は、OSS公開後の運用を安定させるための改善バージョンです。

v0.0.2 で Runtime、Expectation-Driven Design Flow、Review Council Runtime、OSS公開基盤を整えたため、v0.0.3 では実際に使い続けるときの摩擦を減らすことを重視します。特に、fresh checkout 直後の起動性、doctor warning の解消、Runtime log の追跡性、Issue / PR 作成時の運用導線を改善します。

## Goal

このバージョンの目標は、Ariadne を「公開できる状態」から「公開後に迷わず運用できる状態」へ進めることです。

主な観点は次の通りです。

- GitHub Issue / Pull Request のひな形を、v0.0.3 以降の運用に合わせる。
- Copilot / Codex 向けinstructionを日本語化し、`.ariadne/` をAI workflow資産の主配置として扱いやすくする。
- fresh checkout で `db/registries` が空でも、`templates/registries` からruntime registryを復元できるようにする。
- `db/rag` と `work/db/ariadne-knowledge-platform` の責務境界を明確にする。
- workflow doctor / health check のwarningを、運用上意味のある指摘に寄せる。
- 1 workflow 実行を1 trace idで追跡し、Runtime log のsequenceをworkflow全体で連番化する。
- テスト実行で出力した確認ログを `logs/test` 配下へ分け、通常運用ログと混ぜない。
- Runtime pytest UT仕様書と実テストの対応を維持する。

## Implemented So Far

### GitHub運用テンプレート

Issue template は、日本語のversion planを中心に、v0.0.3以降の改善管理に使いやすい形式へ寄せました。

Pull Request template は、Summary、Changes、Verification、Related Issue を自然に埋められる形式に整理しました。Merge時のcommit messageも、semantic commit と Intent / Scope / Decision / Impact を含む定型へ合わせています。

### Copilot / Codex instruction

`.github/copilot-instructions.md` と `.github/instructions/ariadne.instructions.md` は、`.ariadne/` を参照する薄いbridgeとして整理しました。

GitHubが読むファイルは `.github/` に残し、Agent prompt、workflow prompt、schema、shared rule は `.ariadne/` に集約します。

### Registry bootstrap

`templates/registries/` を、fresh checkout用のruntime registry seedとして整備しました。

`db/registries/registry.duckdb` は生成物として扱い、初期起動に必要なsource JSONはtemplateとしてrepositoryに保持します。これにより、`db/registries` が空の状態でも、次のような機能を復元できます。

- `aiwfctl help`
- `aiwfctl env`
- Context First Tool Dispatcher
- Human Gate Policy
- Workflow Doctor

registry source の代表例は次の通りです。

```text
templates/registries/human_gates.json
templates/registries/workflow_help.json
templates/registries/search_terms.json
templates/registries/tool_candidates.json
templates/registries/workflow_environment_profiles.json
```

### RAG / Knowledge責務

`db/rag/README.md` で、Ariadne本体が保持するread model / evidence / retrieval result と、`work/db/ariadne-knowledge-platform` 側で扱う長期knowledge sourceの責務を分けました。

これにより、RAG生成物をどこまでGit管理し、どこから再生成対象にするかを判断しやすくしています。

### Runtime health / doctor

workflow doctor と health check は、registry template、runtime wrapper、test spec、RAGディレクトリなどの運用前提を確認できるように改善しました。

既存warningのうち、fresh checkoutや通常運用で混乱しやすいものは解消し、残るwarningは本来の運用判断に近いものへ寄せています。

### Runtime trace / log

workflowが最後まで通らない原因を追跡しやすくするため、active trace 配下では1 workflow 実行を1 trace idとして扱います。

`trace begin` から `trace end` までの複数 `aiwfctl` command は、同じ trace id を共有し、sequence もworkflow全体で連番になります。

```text
trace begin      -> 00001, 00002
help list        -> 00003, 00004
help markdown    -> 00005, 00006
trace status     -> 00007, 00008
trace end        -> 00009, 00010
```

active trace がない通常commandは、command scoped traceとして扱います。この場合、commandごとにsequenceが `00001` / `00002` へ戻るのは正常です。

### Test log storage

通常運用ログは `logs/runtime/`、テストで生成した確認ログは `logs/test/` に分けます。

workflow trace の結合寄りUTでは、確認用のruntime logを次にコピーします。

```text
logs/test/runtime-trace-cli-integration/sequence/runtime-events.log
logs/test/runtime-trace-cli-integration/without-active/runtime-events.log
```

### Docs maintenance

`docs/reference/documentation-maintenance.md` を追加し、実装、runtime、workflow、schema、template、RAG、registry、GitHub Actions、legal / release運用を変更したときに、一緒に確認するdocsを整理しました。

Runtime pytestを変更した場合は `tools spec-check`、運用判断が変わる場合はDevelopment Notes、生成物やsource of truthの境界が変わる場合は該当reference docsを確認する方針にしています。

## Notes For Next Work

v0.0.3 の残作業では、Runtime UX、help、doctor、Knowledge、Evidence の利用体験を引き続き確認します。

特に、次の点は継続して見ます。

- `aiwfctl help` から必要な操作に迷わず到達できるか。
- `workflow doctor` のwarningが、人間にとって判断可能な粒度になっているか。
- Runtime log と Feedback report が、失敗原因の説明に十分使えるか。
- registry / RAG read model が、fresh checkoutでも再生成しやすいか。
- Development Notes が、後続バージョンのIssueとPull Requestに再利用できる粒度で残っているか。
