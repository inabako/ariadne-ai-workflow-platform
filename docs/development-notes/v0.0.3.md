# v0.0.3 Development Notes

v0.0.3 は、OSS公開後の運用安定化と Runtime UX 改善を主目的とするバージョンです。

v0.0.2 で Runtime、Expectation-Driven Design Flow、Review Council Runtime、OSS公開基盤を整えたため、v0.0.3 では「実際に使い続けるときに詰まる箇所」を中心に改善しています。

## Goal

このバージョンの目的は、Ariadne を公開後も迷わず運用できる状態へ近づけることです。

主な観点は次の通りです。

- GitHub Issue / Pull Request のひな形を v0.0.3 以降の運用に合わせる。
- Copilot / Codex / Cursor / Cline / Claude / Kiro 向け instruction を日本語化し、`.ariadne/` を AI workflow 資産の主配置として扱いやすくする。
- fresh checkout 直後でも `templates/registries/` から runtime registry を復元できるようにする。
- `db/rag` と `work/db/ariadne-knowledge-platform` の責務境界を明確にする。
- workflow doctor / health check の warning を、運用上判断しやすい指摘へ寄せる。
- 1 workflow 実行を 1 trace id で追跡し、runtime log の sequence を workflow 全体で連番化する。
- テストで出力した確認ログを `logs/test/` へ分離し、通常運用ログと混ぜない。
- 結合試験 / E2E 試験を runtime artifact として残し、問題発見、修正指示、再テスト、Human Check までつなげる。
- Kubernetes / k3s を含む IaC 指定時に、アプリ状態確認、互換性評価、gap report、dry-run evidence、E2E evidence へ進める。
- Runtime pytest UT 仕様書と実テストの同期を維持する。

### Registry Bootstrap

`templates/registries/` を fresh checkout 用の runtime registry seed として整備しました。

`db/registries/registry.duckdb` は生成物として扱い、初期起動に必要な source JSON は template として repository に保持します。これにより、`db/registries` が空の状態でも次の機能を復元できます。

- `aiwfctl help`
- `aiwfctl env`
- Context First Tool Dispatcher
- Human Gate Policy
- Workflow Doctor

registry source の代表例は次の通りです。

```text
templates/registries/human_gates.json
templates/registries/workflow_help.json
templates/registries/search_terms.json
templates/registries/tool_candidates.json
templates/registries/workflow_environment_profiles.json
templates/registries/runtime_help_capabilities.json
```

### RAG / Knowledge 責務

`db/rag/README.md` で、Ariadne 本体が保持する read model / evidence / retrieval result と、`work/db/ariadne-knowledge-platform` 側で扱う知識 source の責務を分けました。

通常の RAG と semantic hints は同じ knowledge platform 配下で扱いますが、目的は分けています。

- RAG: 後続Agentが参照する知識 source と検索用 read model。
- Semantic hints: 語彙、文脈、対象ドメイン、運用上の注意点などを検索・dispatch・判断補助に使う軽量ヒント。

### Runtime Health / Doctor

workflow doctor と health check は、registry template、runtime wrapper、test spec、RAG directory などの運用前提を確認できるように改善しました。

warning は、修復可能なもの、人間判断が必要なもの、運用上許容できるものを分けて扱えるように整理しています。

### Runtime Trace / Log

workflow が最後まで通らない原因を追跡しやすくするため、active trace 配下では 1 workflow 実行を 1 trace id として扱います。

`trace begin` から `trace end` までの複数 `aiwfctl` command は同じ trace id を共有し、sequence も workflow 全体で連番になります。

```text
trace begin      -> 00001, 00002
help list        -> 00003, 00004
help markdown    -> 00005, 00006
trace status     -> 00007, 00008
trace end        -> 00009, 00010
```

active trace がない通常 command は、command scoped trace として扱います。この場合、command ごとに sequence が `00001` / `00002` へ戻るのは正常です。

### Test Log Storage

通常運用ログは `logs/runtime/`、テストで生成した確認ログは `logs/test/` に分離しました。

workflow trace の結合寄りUTでは、確認用の runtime log を次のように `logs/test/` へコピーします。

```text
logs/test/runtime-trace-cli-integration/sequence/runtime-events.log
logs/test/runtime-trace-cli-integration/without-active/runtime-events.log
```

### Runtime UX

`aiwfctl status`、`doctor`、`trace`、`log`、`help runtime` 周辺を改善しました。

主な改善は次の通りです。

- `status` の next action を doctor guidance と統合。
- `doctor --repair-*` の dry-run / preview を追加。
- `log summary`、`log tail`、`log grep`、`log export`、`log archive`、`log prune` を整備。
- `status` で直近 event のノイズを抑え、problem event を追いやすくした。
- dry-run plan の `--output` 保存に対応。
- `trace show --problems` と replay / resume hint を追加。
- `doctor` warning の severity / category / repairable / human review を整理。
- `status --summary`、`--verbose`、`--problems` を追加。
- environment / dependency readiness を `status` / `ready` に統合。
- `preflight` と `doctor` の責務境界を docs と runtime help に反映。
- dry-run 対応 command の一覧を `help runtime --json` で機械可読に出せるようにした。

### Integration / E2E Test Runtime

成果物に対する結合試験および E2E 試験を runtime artifact として扱うため、`aiwfctl e2e` を追加・拡張しました。

基本の流れは次の通りです。

```text
test objective
  -> readiness
  -> stub decision
  -> run
  -> observe
  -> verify
  -> review-plan
  -> coverage
  -> explain
  -> final-gate
  -> evidence-package
```

実装済み command は次の通りです。

```text
aiwfctl e2e plan
aiwfctl e2e contract scaffold
aiwfctl e2e contract
aiwfctl e2e readiness
aiwfctl e2e run
aiwfctl e2e observe
aiwfctl e2e verify
aiwfctl e2e review-plan
aiwfctl e2e coverage
aiwfctl e2e explain
aiwfctl e2e final-gate
aiwfctl e2e evidence-package
aiwfctl e2e loop
```

検証契約では、AIにテストを書かせる前に次の項目を固定します。

- objective
- trigger
- preconditions
- expected_route
- expected_state_transitions
- expected_side_effects
- observable_endpoints
- timing_constraints
- ordering_constraints
- duplicate_handling
- retry_expectations
- recovery_expectations
- required_stubs
- failure_signals
- evidence_requirements
- human_review_points

`review-plan` は E2E evidence を Review Council へ渡す bridge artifact を作成します。`coverage` は required evidence の充足状況を確認し、`final-gate` は Human 最終判断を記録します。`evidence-package` は、PR / Human Check / 後続Agent向けに関連 evidence を1つの package へ集約します。

`evidence-package` では `--trace-id` による trace/log 参照、`--output` による `docs/evidence/...` への copy、未解決 `loop.json` の blocker 検出にも対応しました。

### IaC / Kubernetes Preparation

要件定義や設計書に Kubernetes / k3s が指定された場合に備え、IaC 準備工程を runtime 化しました。

重要な判断として、Kubernetes / k3s に限らず IaC 全般では、インフラを組む前に最終的なアプリ状態を確認します。アプリの runtime、port、health endpoint、environment、secret、stateful resource、external dependency、test command が曖昧な場合は、provider-specific IaC へ進まず gap report として止めます。

主な flow は次の通りです。

```text
App Runtime Assessment
  -> Deployment Contract
  -> Gap Report
  -> Kubernetes / k3s Compatibility Assessment
  -> manifest scaffold generation
  -> kubectl dry-run evidence
  -> integration E2E plan
  -> evidence package
```

Kubernetes / k3s boilerplate は `templates/boilerplates/infrastructure/kubernetes-app-template/` に追加しました。仕様差分は spec delta として取り込み、template 本体へ直接混ぜ込みすぎない方針です。
